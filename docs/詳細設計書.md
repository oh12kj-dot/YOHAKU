ADR-005に基づき、取得結果を部屋とは別の商品候補として明示保存する。同じ出典URLと本文SHA256は重複させず、再起動後は通信せず再表示できる。候補は未照合・モデル未生成のままで、正式仕様や配置済みモデルへ自動昇格させない。100件・4MiB上限、厳格な全体検証、保存先ごとの排他と最新内容の再読込、同一場所の一時ファイルからの原子的置換で保全する。不正ファイルは上書きしない。

## 1. 設計判断と実装の境界

編集開始時から写実的な3D空間を操作し、メーカー商品URLから外寸・画像を自動調査して家具を作る。寸法の調査・転記・モデル修正を通常フローでユーザーに委ねない。部屋の内寸はユーザーの実測入力を用いる。

現行のURL調査はADR-004の限定的なローカル処理。YohakuCoreの純粋な検査/抽出と、YohakuのWindows通信/Slate表示を分離する。HTTPSのFLYMEe商品URLだけを受け付け、転送を追跡しない。2MiB上限、12秒期限、同時1件、取消トークンと世代/URL一致で古い応答を破棄する。出典URL/UTC時刻/SHA256/外寸/仕様候補/写真URLを取得し、single-source-unverified・not-generatedとする。SceneDocument、Dirty、履歴、既存モデルを変更せず、保存や正式な仕様版へ自動昇格させない。後述のサーバー型・状態遷移はこの一時結果から自動的に満たされたとは扱わない。

| 決定ID | 採用する設計 | 対応 |
|---|---|---|

| DD-04 | 不変の仕様・アセットと、可変の現在の採用可否を分離する | R-02 |
| DD-05 | 正常例・回復例・未解消負例を分け、保留評価集合を別途固定する | R-03 |
| DD-06 | プロジェクト複製で専用利用権を付与し、元プロジェクトから独立して保持する | R-07 |
| DD-07 | ジョブはownerId・projectIdに所属し、一覧から再接続する。接続回復で生成を再実行しない | R-06 |

## 3. 共通データ規約

- 識別子はUUID文字列。所有者は認証済みsubjectに対応する内部User IDで表し、リクエストのownerIdを採用しない。
- 日時はUTCのRFC 3339で保存・返却し、画面ではAsia/Tokyo等の利用環境に変換する。
- 寸法・座標はmm。保存時は0.001mmの桁へ正規化し、描画時のみ10で割ってUEのcmへ変換する。床面(x,z)/高さyをUE(X,Y,Z)へ対応させ、UE yawは保存yawの符号を反転して度へ変換する。表示桁と保存精度を区別する。
- 右手系、+Yが上。家具ローカル+Xを幅、+Yを高さ、+Zを正面と奥行きの正方向とする。底面外形中央を原点とする。
- 床置き家具の回転はY軸yawのみ。角度はrad、範囲は[-π, π)。任意拡縮・傾斜は受け付けない。
- 浮動小数点値はすべて有限値。負の寸法、ゼロ寸法、NaN、Infinityを拒否する。上限は版付きResourceProfileで定める。
- sceneRevision、generationは単調増加。JSONでは10進文字列で返し、JavaScriptの整数精度に依存しない。
- 取得資料、採用仕様、証拠、アセット、検証ルール、シーン版は不変。変更は新しい版の作成とする。
- JSONの正規化はキー順、数値、null、配列順を規定し、schemaVersionを含めてSHA-256を計算する。HTTPヘッダーや日時を任意に混ぜない。

glTFは右手系・Y上方向等を定義する。取り込み変換は一度だけ適用してアプリ規約に正規化し、方向・単位をメタデータへ残す。[glTF 2.0仕様](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)

## 4. シーンスキーマ・編集状態

### 4.1 保存するシーン

```ts
type Vec3Mm = { x: number; y: number; z: number };
type FurnitureInstance = {
  instanceId: string;
  assetVersionId: string;
  positionMm: Vec3Mm;
  yawRad: number;
};
type SceneSnapshot = {
  schemaVersion: 1;
  layoutId: string;
  sceneRevision: string;
  room: Room;
  furniture: FurnitureInstance[];
  environment: Environment;
  savedViews: SavedView[];
  geometryWarnings: GeometryWarning[];
};
```

| 型 | 必須フィールドと規則 |
|---|---|
| Room | widthMm、depthMm、heightMm、columns、openings、surfaces。床の基準隅を(0,0,0)、室内をX/Z正方向とする |
| 壁 | NORTH/SOUTH/EAST/WESTに対応する安定wallId、始終点、室内法線。部屋変更時も同じ壁IDを維持 |
| Column | columnId、床面位置、widthMm、depthMm、heightMm。室内に収まる矩形 |
| Opening | openingId、wallId、kind=window/door、壁始点からのoffsetMm、widthMm、heightMm、sillMm。ドアはhingeSide、swingDirectionも必須 |
| Surface | surfaceId、対象壁または床・天井、materialId、色、UV尺度・回転、粗さ。UV尺度は実寸に対応 |
| Environment | 環境プリセット、光源ID・位置・種別・強度・色温度、露出。位置はmm |
| SavedView | viewId、名称、positionMm、targetMm、verticalFovDeg、eyeHeightMm。画角の検証範囲はResourceProfileへ固定 |
| GeometryWarning | kind、対象ID群、判定形状の種類、離隔等の値、geometryRuleVersion。サーバーが生成する |

家具寸法、色・サイズ等の購入仕様はassetVersionIdの固定参照から取得し、インスタンスで上書きしない。床置き家具のpositionMm.yは0とし、浮かせる指定を拒否する。柱・窓・ドアの壁外、開口の重複、不正なヒンジ・寸法は拒否する。家具の侵入・はみ出しは警告として保存でき、勝手に縮小・削除しない。

geometryWarningsは保存時の形状判定記録。後から判明した誤寸法等の現在の問題は、シーンを変更せずAssetEligibilityのオーバーレイとして取得する。

### 4.2 ネイティブクライアントの状態（サーバー連携時の設計）

| 状態 | 永続化 | 用途 |
|---|---|---|
| confirmedScene | ローカル操作ジャーナル＋サーバー | 最後に確認したシーン版 |
| pendingCommands | ローカル操作ジャーナル | まだ送信していない操作列 |
| inflightRequest | ローカル操作ジャーナル | 送信内容・操作ID・期待版を固定した要求1件 |
| previewScene | メモリーから再構成 | confirmedSceneに未保存操作を重ねた表示 |
| selection/camera/cutaway | セッション | 選択、操作中の視点、一時壁非表示 |
| jobList | サーバーが正本 | 取り込み・訂正ジョブ。ローカルキャッシュだけに依存しない |

ローカル操作ジャーナルはownerId・projectId・layoutIdで区分する。ログアウトでローカル個人データを消去し、サーバー側ジョブは維持する。ローカル保存領域の消去・容量不足では未保存編集の復旧を保証できないため、保存できなかった時点で明示し「保存済み」と表示しない。

ProductSpecVersionのspec_jsonには商品名・型番・正規URL・色・素材・3軸外寸・元単位・出典版を含める。寸法はdecimal文字列で格納して変換規則を固定する。原資料の取得日時が違うだけで同じ仕様版を乱造せず、正規化した仕様内容と採用証拠集合を基準に版を識別する。異なる版は購入候補で無断統合しない。

### 5.2 所有権・不変性

APIは認証subjectからowner_idを決め、Project所有権を必ずサーバーで確認する。ネイティブクライアントからDB・ストレージへ直接書き込ませない。DB実行ロールは通常API、内部ワーカー、マイグレーションに分ける。所有権のある表にはRLSも適用し、APIロールをテーブル所有者・BYPASSRLSロールにしない。接続プールではトランザクション内だけに認証コンテキストを設定する。

RLSは行へのアクセスを制限するが、テーブル所有者等には例外があるため、アプリ認可・SQL権限・RLSを併用する。[PostgreSQL Row Security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

不変表は通常ロールのUPDATE/DELETEを禁止する。GCは専用経路で参照・保持期限を確認してから削除する。保持中履歴や他プロジェクトの参照をCASCADEで消さない。

## 6. API仕様

### 6.1 共通契約

ベースは `/api/v1`。HTTPS、JSON、schemaVersionを使用する。ネイティブクライアントの認証方式・資格情報の安全な保管・更新/失効はサーバー接続前の別設計で確定し、未実装のまま成功扱いにしない。内部ownerIdとサーバー側の所有権検査は維持する。ローカルのレイアウトJSONへ資格情報を格納しない。

成功応答は `{ data, requestId }`、失敗は `{ error: { code, message, retryable, details }, requestId }`。認可されないProject・Job・Asset参照は存在有無を分けず404。認証なしは401。幾何的な干渉警告は200の結果に含め、形状不正等の拒否と区別する。

| HTTP | 経路 | 入力・結果 |
|---|---|---|
| GET | /projects | 自分のactive Project一覧。削除済みは明示フィルターで取得 |
| POST | /projects | name、operationId、初期部屋 → Project・初期Layout・revision=1 |

## 7. 更新トランザクション・自動保存

### 7.1 共通のサーバー処理

すべてのシーン更新は同じSceneApplicationへ入り、取得済みSnapshotの直接書込を受け付けない。DBは短いREAD COMMITTEDトランザクションと明示ロックを使用する。共通ロック順はProject（ID順）→Project操作台帳→Layout（ID順）→spec_policies（spec_version_id順）→asset_eligibility（asset_version_id順）→Grant（asset_version_id順）→Job→blobとする。使用しない種類は省略できるが、後段を取ってから前段を取り直さない。仕様停止と採用はProjectが異なっても同じspec_policies行で直列化する。外部HTTP・OCR・生成はロック中に実行しない。削除・複製・採用可否変更・アセット公開もこの順を守る。

1. セッション・CSRF・要求スキーマを検証する。
2. Projectをロックし、現在の所有権・active状態を確認する。
3. 操作台帳を照会する。同一ID・同一内容の確定済み結果は期待版判定より先に返す。内容違いは拒否する。
4. 新規操作はLayoutをロックし、expectedRevisionと現在版を比較する。
5. 対象アセットの仕様IDを不変参照から列挙し、常在するspec_policies行をFOR UPDATEでロックする。asset_eligibilityとGrantも上記順で取得し、ロック後に現在の実効採用可否・利用権を再読する。新規採用はblockedを拒否し、履歴継承の例外は別検査する。
6. コマンドを適用し、ID、数値、単位、部屋、寸法不変、配置制限を共通検査する。警告はクライアント値を採用せず再計算する。
7. Snapshot、scene_asset_refs、現行版、Undo関連記録、必要な訂正適用記録、操作応答、outboxを同時に確定する。
8. COMMIT後に応答する。応答喪失時も同一IDを再送して同じ結果を返す。

競合・検証拒否も確定結果として台帳に残す。DB障害等でトランザクション自体がロールバックした場合は未確定であり、同じ要求で再実行できる。汎用の更新ワーカーリースは使わず、同時要求はDBの一意制約と行ロックで直列化する。重い複製はリクエストを中断しても同じoperationIdで確定結果を照会する。

PostgreSQLの行ロックを競合制御の基盤とし、ロック待ち・デッドロックは監視する。内部のデッドロック・一時障害は同じ操作IDで有限回再試行し、結果不明のまま別IDへ変えない。[PostgreSQL Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html)

#### 7.1.1 Project新規作成の冪等性

新規作成は既存Projectに属さないため、通常のscene_operationsではなくowner_operationsを使う。認証済みownerId、operationId、操作種別、正規化した本文ハッシュを照合する。同じownerId・operationId・内容は初回の確定応答を返し、異内容は409で拒否する。別所有者の同じoperationIdは独立した操作であり、他者の結果を参照できない。

1トランザクションでowner_operationsの一意キーを確保し、新Project、初期Layout、初期Snapshot、確定応答を作る。同時要求はこの一意キーで競合させ、初回の確定またはロールバックを待って同じ処理結果へ合流する。既存Projectのロックは取らず、新規作成後に他Projectの操作台帳を取得しない専用経路とする。

応答喪失時は同じPOSTを再送するか、GET /me/project-creation-operations/{operationId}で結果を照会する。未確定の404を受けても別operationIdへ変えず同じ要求を再送する。COMMITされなかった要求は再実行できる。所有者台帳の確定キーと対象IDは所有者のアカウント存続中保持し、Project物理削除でCASCADE削除しない。過去の作成結果再送で削除済みProjectを再作成せず、クライアントは返されたIDの現在状態を別途確認する。

### 7.2 ネイティブクライアントの保存キュー（未実装）

1. 操作完了時、コマンドをローカル操作ジャーナルへ保存してから「未保存」として表示へ適用する。
2. 同じLayoutの送信中要求は1件だけ。未送信の同じ家具のドラッグ結果のみ最後の絶対位置に統合できる。
3. 追加・削除・交換・訂正・Undoの前後をまたいで統合しない。ドラッグ中は見た目だけ更新し、確定時に1コマンドとする。
4. 次の要求を送る直前に確定版からexpectedRevisionを決め、operationId・本文を固定して永続化する。
5. 成功後にconfirmedSceneを更新し、未送信列を重ね直して次を送る。古い応答で新しい版を上書きしない。
6. 通信断ではinflightRequestを固定したまま結果照会・再送する。他のコマンドを先に送らない。
7. 別クライアントとの競合では送信停止。未保存列と最新シーンを表示し、再適用か破棄を選べる。上書きを既定にしない。

競合後の再適用は対象の存在・元アセット等を再検査し、プレビュー後に新operationId・期待版で組み立てる。無関係そうな編集を自動マージしてユーザーに知らせず確定しない。

再読込時は同じownerIdのローカル列を発見し、送信中の台帳結果を先に取得する。成功済みなら列から除去し、未処理なら同じ要求を再送する。配置案切替後もキューを所有範囲ごとに維持し、削除済みProjectへの自動送信を止める。

### 7.3 Undo/Redo

各確定操作に変更前後の対象値と逆操作を記録する。同じLayoutの現行履歴先端に対してのみUndoし、別タブ変更後の古い操作は競合として扱う。Undo/Redoも送信キュー経由で新sceneRevisionを発行する。新しい通常編集でRedo枝を破棄するが、保持対象Snapshotを即時に消さない。

blockedアセットを含む過去状態への復元は、サーバーがその履歴に実在する値だけを復元し、現在の警告を重ねる。任意アセットを履歴と称して注入できない。訂正候補作成ジョブはUndoの対象外で、現在の適用件数だけを再計算する。

## 8. 商品取得・寸法判定

### 8.1 取得手順と出典

URL受付→安全検査→HTML・構造化データ→必要時の隔離ブラウザー→商品画像・寸法図→公式関連ページ・PDF→メーカー型番による公式追加調査の順で進める。画像・PDFは隔離プロセスで解析し、資料ごとに不変のSourceArtifactを作る。

取得対象と同一商品・仕様の関連が確認できない資料は証拠に採用しない。ECサイトの類似商品や画像検索の外観だけから公式仕様を埋めない。公式資料間の転載・共通データ元を記録し、独立根拠を水増ししない。

DimensionCandidateは `axis=W/D/H/unknown`、`role=overall/seat/part/package/unknown`、値・単位、対象仕様、根拠領域を持つ。画像領域は元解像度と矩形、PDFはページ・矩形、HTMLは保存本文の位置とDOM手掛かりを記録する。候補の誤読訂正でも元候補を上書きしない。

### 8.2 Dゲートの実行

| 順序 | 処理・失敗時 |
|---|---|
| D1 | メーカー商品ID・型番と仕様選択を照合。候補が複数ならawaiting_variantで待機 |
| D2 | 全体外寸の3軸、単位、寸法線・部位対応を確認。不明は公式調査へ戻す |
| D3 | 異なる公式記述の値・軸を照合。単一資料なら校正済みの独立解析経路を使う |
| D4 | 発見済み矛盾を確認。仕様違い・丸め・状態差を説明できない場合は採用しない |
| D5 | 候補・資料・比較結果・ルール版を固定し、採用値への参照を検査 |

単位変換例は `cm × 10 = mm`。丸め区間が重なる場合も平均せず、優先する原記載値と根拠を検証プロファイルの規則に従って選ぶ。幅と奥行きをモデルの見た目に合わせて都合よく交換しない。

Dゲート結果は `pass/fail/indeterminate`。全passでのみ仕様版を発行する。failは誤候補を排除したことを表し、直ちに調査全体の終端を意味しない。追加調査で別の正候補に全passなら処理を続けられる。上限まで解消しなければJobをfailed、理由をDIMENSIONS_UNRESOLVEDとする。

|---|---|---|
| PageFetch | 許可済みURL、予算、取得方式 | 本文・関連URL・ステータス・ハッシュ |
| DocumentExtract | 不変Artifact、抽出規則版 | 候補、部位・領域、元の値・単位 |
| ProductResolve | 選択仕様、公式候補群 | 一致・不一致・選択候補と根拠 |

## 9. 非同期ジョブ・再接続

### 9.1 状態遷移

| 現在 | 条件 | 次状態 |
|---|---|---|
| queued | 有効Projectで試行取得 | fetching |
| fetching | 初回の採用入力を固定して取得成功 | extracting（初回は現generationにmanifestを1件発行） |
| fetching | 既存の採用入力へ資料を追加・変更して確定 | 新generationのextracting（下流試行を無効化） |
| fetching | 探索を終えても採用入力は変更しない | 同generationのextracting（新しい段階試行として再開） |
| extracting | 候補抽出完了 | resolving |
| resolving | 購入仕様の選択が必要 | awaiting_variant |
| awaiting_variant | 対象候補から明示選択 | resolving（必要な入力を新世代へ固定） |
| resolving | 追加の公式資料が必要・予算あり | fetching（探索）。採用入力確定時に新generationへ移る |
| resolving | D1〜D5合格、入力を固定 | generating |
| generating | 公式モデル取得または生成結果取得 | validating |
| validating | 再生成で解決可能・予算あり | generating（新しい生成試行） |
| validating | M1〜M6合格 | ready |
| 各非終端状態 | 確定したキャンセル | cancelled |
| 各非終端状態 | 回復不能・予算到達 | failed |
| failed/cancelled | 利用者の明示再試行 | 新generationのqueued |

readyは当該世代の終端。別仕様への変更は旧結果を上書きせず、別世代・結果版として扱う。進行中の仕様変更は世代を増やし、古い外部処理へ停止を試みる。結果のハッシュが一致しても旧世代の通知で現在状態を更新しない。

generationは選択仕様・採用入力manifestの世代を識別する。初回の入力確定は現generationにmanifestを1件作る。以後、採用する資料集合・資料内容・仕様・処理設定を変更する場合、generationを増やし、新しい不変manifest・入力ハッシュ・attemptIdを同時に確定する。まだ探索している資料は採用入力と分離し、発見しただけでは世代を変えない。追加・変更を採用しない場合も、現在のfetching状態から旧試行が勝手に下流確定しないよう遷移元・current_attempt_idを検査する。

世代変更時は旧世代の抽出・解決・生成・検証の確定権限を失効させる。再利用は新試行が依存入力とルール版の一致を確認して明示的に登録し、旧結果の後着通知をそのまま再利用しない。Job全体の費用・取得件数・生成回数の累積予算は世代をまたいで保持する。

attemptIdは段階ごとの試行、lease_epochは同試行のワーカー所有権を識別する。入力を変えない内部リース回復ではgenerationを増やさずlease_epochを増やす。Jobがタイムアウトで終端failedになった後の利用者による再試行は新generationとする。外部要求の論理的な冪等キーは内部リース更新だけでは変えず、既存の外部requestIdへの照会を優先する。

### 9.2 実行・外部通知

ジョブはDB outboxから配送し、配送は重複し得る前提とする。ワーカーはJobAttemptをリース取得し、世代・入力ハッシュ・lease_epochを持って実行する。タイムアウト時はlease_epochを増やし、旧ワーカーの確定を拒否する。

外部生成の開始要求に事業者対応の冪等キーを付け、provider_request_idを保存する。タイムアウト後に状態照会できる場合は照会を優先する。冪等性も状態照会もない事業者では、課金済みか不明な要求を自動再送しない。結果不明として明示し、再実行の判断へつなげる。

コールバックは署名・時刻・外部requestIdを検証し、当該試行へ対応付ける。確定時はProjectの状態・lifecycle_epoch、Jobの現行世代・試行・入力ハッシュ・lease_epoch、許可された遷移元を同一トランザクションで再検査する。コールバックの値だけで仕様・ownerId・projectIdを決めない。

ready発行では、非公開ストレージへの構成物保存・ハッシュ検証を先に終え、7.1節の順でProject・仕様ポリシー・対象アセット状態・Jobを検査する。仕様ポリシーが既にblockedなら旧根拠で新たにreadyを発行せず、再調査または理由付き失敗へ戻す。既存ポリシーを初期eligibleで上書きしない。検証記録、アセット版、新規アセットの初期採用ポリシー、Grant、Job結果、Project通番付きイベント、outboxを原子的に確定する。DB確定失敗の孤立staging blobはGC対象であり、UIへ公開しない。キャンセル・削除・完了の競合は先に確定した状態を返す。削除後は旧世代を無効化し、後着成功でGrantを作らない。

### 9.3 予算・再試行の初期設定案

| 対象 | 初期設定案 | 超過時 |
|---|---|---|
| 資料取得 | 1調査で関連資料20件、合計100MiB、PDFは50ページまで | 追加自動調査を停止し理由を保存 |
| 単一取得 | 接続・応答の上限30秒、サイズ上限20MiB | 失敗候補として別の公式経路を調査 |
| 技術的再試行 | 通信等の一時障害は同一要求で最大3回、指数バックオフとjitter | failedまたは結果不明 |
| 3D生成 | 初回を含め最大2回。外部費用上限をJob開始時に予約 | 予算超過で停止、勝手に追加課金しない |
| 調査全体 | 生成待ち・仕様選択待ちを除き10分 | 未解決情報と調査済み根拠を提示 |

これは運用検証前の設定案。費用は事業者の価格が確定してから通貨・金額上限を設定する。費用上限が未設定の事業者を有効にしない。再試行の全回数を通じた費用を集計し、毎試行で上限をリセットしない。

### 9.4 一覧・再接続・認可

Project行のlast_event_seqを、行ロック下で1増やしてproject_event_seqを発行する。Job状態更新、job_revision増加、job_events、outboxを同じトランザクションで確定し、同じProject内では通番と確定順を一致させる。Job内のjob_event_seqは診断用で、SSE再開には使わない。ロールバックした通番は公開せず、独立したDBシーケンスの採番順を確定順と見なさない。

SSEのidは `projectId:project_event_seq` とする。認可済みProjectとIDのProjectが一致することを確認し、Last-Event-IDより大きい確定イベントをProject通番昇順で取得する。outbox通知は起床の合図であり、通知の到着順ではなくDBの確定イベントを配信する。クライアントはIDで重複排除し、切断時は最後に適用したIDから再開する。

保持境界はProjectのretained_event_floorで管理し、古いイベントを削除するときに同時更新する。初期保持案は7日。カーソルが保持下限の直前より古い場合は配信開始前に409 EVENT_CURSOR_EXPIREDとし、将来の通番・別Project・不正形式は400で拒否する。Projectの所有権・active状態は接続時と配信継続中に検査する。

初回・期限切れ再接続では、認可済みSSEが通知する現在のwatermarkからイベントをバッファしつつ、現行Job一覧を読み直す。初期同期の一覧は状態で除外せず、変化しない `(created_at, id)` の署名付きカーソルで全ページ取得する。各Jobのjob_revisionで新旧を比較し、一覧とバッファ済みイベントを統合する。これによりページ走査中の更新・新規Jobも反映し、古い一覧応答で新しい状態を戻さない。画面の状態フィルターは統合後に適用する。通常の状態別一覧にも安定した作成順を用いる。

仕様選択待ち・処理中・完了未配置・失敗を一覧から再発見できる。キャンセル済みも履歴フィルターから確認し、retryを明示できる。再ログインは既存処理への再接続だけを行い、再生成を始めない。

## 10. 3Dモデル・計測形状

### 10.1 アセット構成

manifestにはassetVersionId、specVersionId、profileId、単位、原点、正面、採用寸法、render/coarse/detailの構成ID・SHA-256、素材参照、検査結果を持つ。GLB内の任意の外部参照は公開前に内部化するか拒否し、ロード時に第三者URLへアクセスさせない。

| 構成 | 用途・条件 |
|---|---|
| render | 写実表示。GLBのm単位。アプリのmm規約との変換を固定 |
| coarse | 実寸の向き付き外形箱または保守的凸形状。mmで保持。概算距離・衝突候補に使用 |
| detail | 描画モデルから同じ変換で生成した三角形形状、または検証済み簡略形状。詳細距離・干渉用 |
| textures | baseColor、normal、roughness、metallic等。色・非色データの扱いを固定 |

### 10.2 Mゲートと追加のM6

M1〜M5は基本設計の寸法・構造・投影輪郭・素材・負荷を検査する。M3は照合可能な2方向以上とIoUの初期閾値0.85を起点に校正する。画像不足や視点推定不能を、自動的に合格へ落とさない。

M6は形状間の整合を検査する。各構成の単位・原点・正面・変換・外寸を検査し、renderとcoarse/detailが同じ座標へ写ることを確認する。構成物を最適化・差し替えたらM1〜M6を再実行する。

- coarseはrender外形を検査許容差内で包含する。凸形状では全render頂点の内包と辺・面を検査し、過大な余剰をカテゴリ別プロファイルで制限する。余剰距離の初期案は各方向10mm以下、原点・軸の差は0.1mm以内とする。外形箱の凹部を埋めることによる内部の過大判定は許容するが、詳細な干渉と呼ばない。
- detailをrenderそのものから生成する場合は面・頂点・変換の対応を固定する。簡略化する場合は双方向の表面間誤差、穴・主要部位、外形差を検査する。初期許容案は表面誤差2mm以下で、近傍探索を誤差上限付きで実施する。単なる少数点サンプルで最大誤差保証と扱わない。
- 計算できない条件はindeterminateにし、未検証detailから詳細値を表示しない。任意の簡易形状への黙った差し替えはしない。renderから検証可能なdetailを再作成し、解消しなければreadyを発行しない。

これらの値は校正前の案であり、カテゴリを有効化する前に正解付き形状で評価してQualityProfileへ固定する。詳細判定の誤差は生成された外形に対する計算誤差であり、未観測の実物形状の誤差を保証しない。

### 10.3 距離・衝突・交換

家具の外寸ラベルは仕様版のW/D/Hを使う。壁基準交換は基本設計の符号付き離隔 `d = min(dot(n, v-p))` とし、向き付き外形箱の8頂点を用いる。交換先の中心を元中心へ仮配置し、`n * (d_old-d_new)` を加える。沿壁方向の中心、yaw、接地高さを維持する。

簡易判定はAABBで候補を絞り、OBB/凸形状で再判定する。coarseの重なりは「衝突候補」。detailの三角形交差・閉形状内包を確認して「重なり」とする。距離は形状間の最短値を求め、重なり時は0と重なり状態を別表示する。壁平面の負の離隔とは意味を分ける。

ドアはヒンジ・開き方向・最大角度から開閉軌跡を生成する。簡易の掃引領域を候補とし、必要時に詳細形状で確認する。壁の開口部と実際の壁面を区別し、無限平面の離隔が負でも、有限壁の干渉とは別に表示する。

UIは「概算」「詳細形状による計算」「形状の一部は推定」を区別する。通路幅の目安は利用者設定であり、安全・快適を保証する判定にしない。

## 11. 採用可否・訂正・購入候補

### 11.1 現在の採用可否

| 状態 | 新規追加・交換先・家具複製 | 既存配置・履歴・案複製 | 表示 |
|---|---|---|---|
| eligible | 許可 | 維持 | 出典と通常の精度区分 |
| caution | 許可、注意を表示 | 維持 | 外観改善候補等の理由 |
| blocked | 拒否 | 継承・復元のみ許可 | 既知の誤り、訂正状態。該当の照合済み表示を取り消す |

申告だけでblockedにしない。自動再調査のDゲート・検証根拠で誤商品・誤仕様・誤外寸が確認された場合、常在するspec_policies行をロックし、spec_advisoriesへ履歴を追加して同じトランザクションで現在状態をblockedへ更新する。当該仕様を参照する全アセットへ即時に実効反映する。外観だけの問題はasset_eligibilityへ記録する。候補がまだ生成できなくても、確認済み誤寸法への警告は遅らせない。

実効状態はspec_policiesとasset_eligibilityの厳しい方とする。spec_policiesは仕様版と同時に作成し、旧版データを移行する場合も全仕様分を補完してから新規採用を有効化する。advisory未作成でも必ず存在するこの行を、新規採用・仕様停止・アセット公開が同じ順でロックする。停止が先に確定すれば後の新規採用を拒否し、採用が先ならその既存配置へ警告を表示する。後継候補があること自体と、旧版の誤りが確認済みであることを混同しない。

既存配置を動かしたり消したりしない。誤寸法なら旧寸法を「取り込み時の値・誤り確認済み」と表示し、その値による空き寸法にも警告を付ける。購入候補は未反映の固定仕様を示しつつ、誤仕様を確認済みの商品として購入判断へ誘導しない。ユーザー操作なしの寸法差し替えは行わない。

### 11.2 訂正の流れ

依頼受付→調査→新しい仕様・アセット候補→候補比較→選択した配置へApplyCorrectionを送る。依頼の調査状態と、配置ごとの現在適用有無は独立させる。

同一Layoutの対象は一括確定。別Layoutは別操作とし、成功・競合・未実行を区別する。現在の適用件数は、当該request_id・candidateAssetVersionIdに対応するCorrectionApplicationの(layoutId, instanceId)を重複排除した集合に限定し、そのLayoutの現行Snapshotが候補版を参照するものだけを数える。当該依頼の適用記録がない通常追加・交換や、別依頼だけで採用した家具を含めない。適用後の削除、別版への交換、Undo/Redoも同じ集合で再計算する。これは当該依頼の適用履歴を持ち現在候補版を使う件数であり、履歴のあるIDが通常交換で同じ候補へ戻った場合も含む。直近操作の因果、未適用の訂正対象候補数、同じ改善版を使う家具総数を表示する場合は別の指標とする。

### 11.3 購入候補

Snapshotの固定参照からspecVersionId単位で集計する。行は商品名、メーカー、型番、サイズ、色・素材、数量、正規URL、配置ID群、取り込み時刻、現在の警告を持つ。版が異なる同商品は別行として表示する。

価格・在庫は必須にせず、もし将来取得しても取得時刻付きの最新情報として分離する。商品URLを開くときもサイズ・色を一覧に残し、指定できないURLで同じ仕様が選択済みと誤表示しない。

## 12. プロジェクト複製・利用権・削除

### 12.1 複製

初期版のプロジェクト複製は、各active Layoutの指定した現行版を新Projectの初期版へコピーする。過去のUndo/Redo履歴・取り込みジョブ・費用・進行中処理・未配置結果・訂正依頼履歴はコピーしない。この範囲を複製画面に示す。既知の誤り・推定箇所等の警告は引き継ぐ。

1. 元Projectの所有権とactive状態をロック下で確認し、指定Layoutの版を固定する。
2. 新Project・新Layout・新instanceIdを発行する。家具の固定アセット版と部屋・環境・保存視点をコピーする。対象IDを対応付け、形状警告は新IDで再計算する。
3. 参照する全アセットについて元の利用権を検査し、新Project用AssetAccessGrantを作る。origin_type=project_clone、origin_id=operationIdとする。
4. 新Projectのシーン、参照、利用権、操作応答を同一トランザクションで公開する。失敗時は全体をロールバックする。

元ジョブの所属を変えず、新Projectは元Projectの存続に依存しない。blocked版は履歴継承として同じ配置内容に限って保持でき、新規Add等の例外権限は付与しない。利用権と新規採用可否は別検査とする。

同一Project内の配置案複製ではProject用Grantを共有し、部屋・家具・環境は複製後に独立する。別利用者への共有・Project移譲は初期版に含めない。

### 12.2 配信と削除

モデルと資料の物理保存は非公開とし、アセット構成物の配信は認可ゲートウェイ経由に統一する。Project状態とGrantを要求ごとに確認する。ストレージの直接署名URLをクライアントへ返さず、内部の短期URLはサーバー内部だけで使用する。削除・権限失効の確定後は新規配信要求を拒否する。既に端末へダウンロード済みのデータを遠隔消去できるとは扱わない。

Project論理削除ではlifecycle_epochを増やし、Job世代を無効化する。確定済みシーン・Grant・履歴は復元期限まで保持し、一覧・操作・新規配信を止める。初期保持案は30日とし、運用方針として表示してから適用する。復元でもepochを増やし、古いワーカー結果を受け付けない。中止した生成を自動再開しない。

### 12.3 GC

次のいずれかが参照するアセット・資料・blobを削除しない：active Projectの現行版、保持中のUndo/履歴、復元期限内Project、保持中未配置結果、有効な別ProjectのGrant、進行中試行・確定待ち出力。

GCはmark→隔離→最終再照合→物理削除の順とする。参照発行と削除はblob行の状態をロックして競合させ、deletingのblobへ新Grantを作らない。元Projectを削除しても複製先の参照があれば保持する。GC用の単なる参照カウンターだけを唯一の根拠にせず、正規化された参照から再検査する。

結果破棄は一覧上の未配置結果の保持を解除する操作とし、参照中アセット・履歴・他Projectの利用権は消さない。Grantを失効する場合は全保持参照が不要であることを確認する。

## 13. 写実描画・操作

### 13.1 描画パイプライン

1. UE/DX12/SM6・描画対象サイズ・GPUとメモリー予算を能力検査する。未対応なら対応状況を表示し、写実表示できたと装わない。
2. 認可済みmanifestを取得し、構成物のハッシュと許可形式を検証して読み込む。
3. mmのシーンをUEのcm/座標軸へ変換し、PBR素材、環境マップ、窓光、室内灯を同じ座標系へ配置する。
4. シャドウ・接地表現・間接光近似・反射・トーンマッピングを適用する。壁・窓の変更で光の遮蔽を更新する。
5. 家具・照明・カメラが変わると描画と必要な影を更新する。保存完了を待たずプレビューする。
6. 操作停止後は影・反射等を高精細化できるが、同じ幾何形状・配置・素材を維持する。

静的な壁・家具に焼き込んだ影を移動後も残さない。商品写真から素材を作る際も照明の焼き込みを調整する。画像生成で画面全体を置き換える処理を配置操作の主要経路にしない。PBRと影を使うだけで写実品質達成とせず、基準画像・操作動画との評価を通す。

### 13.2 操作仕様

| 操作 | 動作 |
|---|---|
| クリック | 家具選択。空き床で選択解除 |
| 床面ドラッグ | 選択家具を床面へ投影して移動。ポインター開始時の掴み位置を維持 |
| 回転ハンドル・数値 | yaw変更。スナップは切替式で、寸法は固定 |
| カメラ操作 | 家具操作と別ボタン・修飾キー。選択家具の位置を変更しない |
| Delete / Undo / Redo | 対応コマンドへ変換。テキスト入力中は編集キーを奪わない |
| 壁への吸着 | 基準外形箱で離隔を0に合わせ、吸着線と変更量を示す |
| 視点切替 | 俯瞰、室内、座位。室内移動は壁・柱を通り抜けない |
| 画像書き出し | 現在の描画シーンをPNG出力。revisionと未保存有無をメタ情報へ記録 |

カメラの初期eyeHeightは立位1,600mm、座位1,100mmを設定案とし自由に変更できる。画角は初期50度、通常調整範囲30〜90度をResourceProfile案とする。既定値で実際の視覚を厳密に再現すると保証しない。保存視点だけをサーバーへ保存する。

読み込み中は既存の写実シーンを維持し、未準備家具を実寸再現済みの汎用箱として置かない。配置操作はモデルと必要形状が準備できてから有効化する。

### 13.3 性能測定と予算

基準シーンはフルHD、家具20点、表示合計100万三角形以下、原則2Kテクスチャとする。端末・OS・UEビルド・GPU・ライブラリー版・電源状態・表示ピクセル比を固定する。10秒ウォームアップ後、定義したカメラ移動・家具移動・回転を60秒間実行して測定し、3回の各結果を残す。

| 指標 | 暫定合格目標 |
|---|---|
| 操作中フレーム時間 | p95 ≤ 33.3ms |
| 入力から描画への反映 | p95 ≤ 100ms |
| 停止後の静止品質到達 | 2秒以内 |
| 品質 | 操作中も素材・光・影を維持し、家具の数・位置・外形を変えない |

ResourceProfileは対応端末区分、最大インスタンス・三角形・テクスチャ展開容量・光源・部屋寸法・API本文容量・取得予算を持つ。現時点の20点は測定条件であり、無制限の配置性能の保証でも、確定した製品上限でもない。プロファイル未校正の端末区分は正式対応にしない。予算超過は追加前に明示し、既存家具を消したり画面を線画へ切り替えたりして隠さない。

## 14. 画面ごとの状態・例外

| 画面 | 主要状態 | 動作 |
|---|---|---|
| Project一覧 | loading/ready/empty/error/deleted | 再開・複製・復元の対象を明示。失敗を空一覧と同一表示にしない |
| 部屋設定 | editing/invalid/unsaved/saving/conflict | 不正な開口等は箇所を示す。干渉は警告。保存失敗で入力を消さない |
| メイン編集 | ready/loadingAsset/dirty/saving/offline/conflict | 未保存件数と状態を表示。候補・保存・生成の完了を別に示す |
| 取り込み | fetching/extracting/awaitingVariant/generating/validating/ready/failed/cancelled | 正確なパーセントを出せない段階は段階名と経過時間を示す |
| 交換 | selecting/preview/invalid/committing/conflict | 同一カメラ・照明で比較。中止で元家具を維持 |

ユーザー向けエラーは「何が起きたか」「入力・配置が保持されたか」「次にできる操作」を短く示す。処理内部の世代・ハッシュは診断詳細へ置き、通常画面の説明に持ち込まない。

家具選択、移動の数値入力、回転、削除、取り込み、訂正依頼はキーボードでも操作可能にする。警告は色だけに依存せず、ラベルと対象を示す。

## 15. セキュリティ・データ保護

- URLはhttp/httpsのみ。認証情報付きURL、ローカル・プライベート・リンクローカル・メタデータ宛先等を拒否する。DNS解決後の実接続先、リダイレクト先、ブラウザーのサブリソースも出口制御で検査する。
- 取得ブラウザーには利用者のCookie・ログインセッション・内部ネットワークを渡さない。出典のテキストをAIへの命令として実行しない。
- HTMLをそのままアプリへ挿入しない。PDF・画像・GLBは形式、サイズ、展開量、外部参照、処理時間を隔離環境で検査する。
- Job・訂正依頼・操作台帳・配信・SSEは毎回Project所属と現在の認可を確認する。クライアントからownerIdやストレージキーを指定させない。
- 外部事業者に送るのは必要な商品素材・寸法に限定し、部屋・配置案・ユーザー情報を送らない。
- 生成結果・資料の利用条件と取得日時を記録する。権限外の素材・データを、共通キャッシュ経由で他者に公開しない。
- シークレットはサーバー側の管理基盤へ置き、クライアントの環境変数・ログ・URLへ載せない。機密クエリやセッションをログから除く。
- Project削除後の新規データ取得を止める。端末へ取得済みのデータとサーバー配信停止を区別する。

URL取得の対策はネットワーク境界も含め実証する。[OWASP SSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)

## 16. 評価集合と品質プロファイル

| ケース区分 | 期待結果 |
|---|---|
| 正常例 | 正しい仕様・3軸寸法を自動取得し、各ゲート合格後にready |
| 回復例 | 初回誤候補は不採用。公式追加調査・独立解析で解消し、正しい値とモデルの全合格後にready |
| 未解消負例 | 調査上限でも矛盾・不足・取得拒否等が残り、理由付き非ready |
| 保留評価集合 | 規則調整に使わず、上記区分それぞれの期待結果に一致 |

Manifestには商品URL・仕様、カテゴリ、ページ形式、取得資料版、独立に確認した正解、期待する状態系列、予算、ケース区分を固定する。3メーカー各10商品以上の正常例に加え、各失敗分類の回復例・未解消負例を用意する。回復し得ない分類に無理に回復例を作らず、適用外の理由を残す。

保留集合は各メーカーの正常商品3件以上、適用する回復分類と未解消負例分類それぞれ1件以上を最低案とする。同じ商品・画像・資料の転載を開発集合へ重複させない。保留集合を見て修正したら新しい保留集合に置き換える。

初回抽出成功、回復後成功、誤候補の早期採用、最終非ready、モデル破綻の通過を分母別に報告する。回復中に誤モデルをreadyにしてから直しても合格にしない。保存資料の回帰と実URLの取得成功を別結果とする。

Profile公開条件は、固定集合で期待結果に一致すること、D/M各規則・閾値・単一資料経路の校正記録があること。IoUや誤差の数値だけで写実性を保証せず、13章の基準シーンと操作動画も評価する。今回の文書には実測した校正結果は含まれない。

### 17.2 試験層

GeometryKernelとSceneDomainは独立した期待座標・形状で単体検証する。DB統合では実際のPostgreSQLで並行トランザクション、ロール権限、台帳、GCを検証する。HTTPでは認可・再送・コールバック署名・世代を検査する。ネイティブE2Eでは保存キュー・復旧・写実操作を確認する。

取得ワーカーのfixture試験は資料解析の回帰であり、実サイト取得の証拠にしない。生成サービスのモックは状態機械の試験であり、モデル品質の証拠にしない。ヘッドレス画面の画像一致だけで実機性能・写実品質を合格にしない。

試験結果には設計版・実装commit・Profile・Manifest・依存版・端末条件を残す。負例が拒否されたことと正常・回復例が成功したことを両方確認する。

## 18. 運用・配備・復旧

API、取得ワーカー、生成ワーカー、形状ワーカーを別プロセスにし、取得環境のネットワーク権限を最小化する。DB・ストレージ・外部サービスの資格情報は役割ごとに分ける。Web/APIは同一オリジンを基本とし、開発・検証・本番のDB、素材、APIキーを分離する。

マイグレーションは追加→読み書き対応→旧形式移行→削除の順とし、不変アセット・Snapshotを直接書き換えない。新しいschemaVersionの読み込み不能時は保存を止め、古いクライアントで上書きしない。バックアップではDBとオブジェクト参照を同じ復旧点へ合わせ、復旧後にblob欠落・ハッシュ・Grant・outboxを整合確認する。

| 監視対象 | 指標・検知 |
|---|---|
| 取得・生成 | 段階別成功、回復、未解消、滞留、外部費用、重複要求 |
| データ | 操作競合、結果不明、readyなのにGrantなし、参照blob欠落、GC拒否 |
| 編集 | フレーム時間、入力応答、アセット読み込み失敗、未保存時間 |
| セキュリティ | URL拒否、認可拒否、署名不正、個人情報のログ混入 |

requestId・jobId・generation・operationIdで診断し、画像・部屋データ・機密URLを通常ログへ出さない。外部サービス停止時は生成を止めて既存の編集・保存を続け、失敗のたびに別の有料要求を増やさない。

バックアップ頻度、RPO/RTO、料金プラン、正式保持期間、基準端末は運用開始前の確定事項とする。文書で仮の復旧目標を達成済みとして扱わない。

## 19. 実装順序と完了判定

1. 実商品でURL→寸法→3D→写実編集の縦断検証を行い、RendererAdapter・生成先・Profileの校正手段を判断する。
2. contracts、GeometryKernel、SceneDomain、DB制約と共通コマンドAPIを実装し、保存・復旧・認可を確認する。
3. 取得・抽出・Dゲート、世代管理、費用制御、一覧・再開を実装する。
4. M1〜M6、アセット公開・Grant・配信、写実エディター、計測・交換を統合する。
5. 訂正・採用可否・購入候補・Project複製・GCを統合し、DT-01〜DT-20を検証する。

縦断検証で形状品質や写実編集が成立しない場合は未達を記録し、対応カテゴリ・エンジン・提供方式を再検討する。後処理だけの実写化、汎用箱、寸法手入力で代替して完成としない。

| 未確定項目 | 実装・提供前の確定条件 |
|---|---|
| レンダラーの最終採用 | 基準端末・基準シーンで画質と性能を実測 |
| OCR・画像理解・3D生成の事業者 | 実商品でD/Mゲート・費用・時間・データ条件を評価 |
| QualityProfile | 校正結果・正常/回復/負例/保留集合がそろう |
| 認証・クラウド・ストレージ製品 | 本文の認可・配信・復旧契約を満たす統合検証 |
| 利用上限・費用・正式保持期間 | ResourceProfileと運用方針を確定し画面へ表示 |

これらを未選定のまま外部連携・本番提供の完成を宣言しない。インターフェース内の開発は可能だが、モックによる成功と実連携成功を分けて報告する。
